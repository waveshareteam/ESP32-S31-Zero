The enabled matrix is **12 projects × 1 experimental lane**, version `6.2.0-dev-08e0d30a74ad`. Its full commit is pinned and `experimental: true` is propagated to job names and package manifests. All 12 builds and archives remain required for release publication. A stable framework release is not the same as stable target support. Empty matrices still fail explicitly. No moving `master` build is used. Arduino is absent and no FQBN is invented.

Official migration guides inspected: [5.5 → 6.0](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/migration-guides/release-6.x/6.0/index.html), [6.0 → 6.1](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/migration-guides/release-6.x/6.1/index.html). The pinned development commit contains the 6.0 and 6.1 migration guides but no separate 6.2 migration directory. Its 6.1 notes cover UART wakeup API deprecation, MIPI DPI callbacks and fast reflash behavior; no unrelated workaround was introduced. Existing projects already use split `esp_driver_*` dependencies. This audit does not certify API compatibility by compilation.

## Component policy

- Examples 01–10 use framework components. Their explicit `idf: "*"` manifest entry records the resolved framework in a lock; it does not bypass the centrally pinned support gate. The small local RMT encoder in example 02 is retained; replacing it with a managed LED component requires verified ESP32-S31 support for the selected revision.
- Example 11 already requests `espressif/esp_lcd_touch` 1.2.1, `espressif/esp_lcd_touch_gt911` 1.2.1, `espressif/esp_lvgl_adapter` 0.6.4 and `lvgl/lvgl` 9.5.0. These direct requests resolved successfully in the independent first-pass dependency audit; see [resolved dependencies](dependencies.md). The registry page for [adapter 0.6.4](https://components.espressif.com/components/espressif/esp_lvgl_adapter/versions/0.6.4) exists and declares IDF >=5.5 / all targets; that metadata is not proof of a successful ESP32-S31 build. Its local GT911 filtering, panel composition and fixture tests are product adapters, not third-party driver copies.
- Example 12 retains `espressif/iperf-cmd ~1.0.2`, `esp-qa/wifi-cmd ~0.2.7`, `esp-qa/ping-cmd ~1.0.0`. The `cmd_system` component comes from the exact pinned IDF checkout. The ranges resolved to wifi-cmd 0.2.12, iperf-cmd 1.0.3, ping-cmd 1.0.0 and transitive iperf 1.0.3 in this audit; no hand-written lock file is supplied.
- Component Manager 3.1.2 is pinned in the central lane and installed by CI. Generated `dependencies.lock` files are ignored per project because different framework lanes resolve independently. CI must generate a lock, package it verbatim, and record its SHA-256 plus the framework commit. Archive publication fails if it is absent. Preserve the published lock with the archive when reproducing a release. Ranges can resolve differently over time; a deterministic archive does not mean dependency resolution is immutable.
- `managed_components`, local `sdkconfig`, build output, generated board code and downloaded firmware are ignored. Keep `sdkconfig.defaults` and source manifests.

For shared board support, use the [upstream Waveshare components repository](https://github.com/waveshareteam/Waveshare-ESP32-components) and [hardware follow-up](hardware.md). No unverified board definition is substituted for this product.
